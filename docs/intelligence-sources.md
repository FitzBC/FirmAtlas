# 漏洞情报源与同步策略

本文记录 2026-08-05 核对过的首批官方接口。任何外部字段都先保存来源原文，再规范化为内部漏洞记录和受影响声明。

## 首批数据源

| 来源 | 用途 | 同步策略 |
| --- | --- | --- |
| [NVD CVE API 2.0](https://nvd.nist.gov/developers/vulnerabilities) | CVE、CPE 适用性、CVSS、CWE 和修改时间 | 用 `lastModStartDate/lastModEndDate` 增量拉取；游标重叠以容忍迟到修改 |
| [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) | 已知在野利用及加入日期 | 获取官方 JSON，按目录版本/日期去重；变化触发风险重评估 |
| [OSV API](https://google.github.io/osv.dev/api/) | 开源组件精确版本与 purl/生态关联 | SBOM 批量查询；保留 OSV ID、别名和版本事件 |
| [FIRST EPSS API](https://www.first.org/epss/api) | CVE 利用概率与百分位 | 每日同步当前值；按日期保存时间序列快照 |
| 厂商安全公告 | 设备型号、固件版本、修复版本和缓解措施 | 每个厂商独立适配器；保留原文摘要、发布日期、修订时间和链接 |

## 规范化原则

- 外部标识是漏洞记录的别名，不作为内部主键。
- 同一来源的修订不覆盖历史原文；保存抓取时间与源端修改时间。
- CVSS、KEV、EPSS 是不同含义的风险信号，不合成“真相分数”。
- CPE 与 purl 都是候选生成线索，不能单独证明具体固件受影响。
- 厂商公告与通用组件漏洞分开建受影响声明，允许范围冲突。
- 撤回、拒绝和更正记录必须传播到已有漏洞匹配。
- 每次同步记录游标、请求范围、响应摘要、解析器版本和错误。

## 匹配策略

1. 用精确外部坐标、别名和规范化名称生成候选；
2. 解析并比较版本范围，同时保留原始版本字符串；
3. 用文件哈希、构建信息、符号、配置和补丁特征增强或削弱证据；
4. 用接口暴露、服务启用状态和通信可达性描述影响上下文；
5. 输出匹配理由、反证、置信度和验证结论，不只输出布尔值。

## 更新与提醒

- 新漏洞或新增受影响范围：匹配相关存量组件；
- KEV 新增或 EPSS 显著变化：只重算优先级和提醒；
- 厂商发布修复版本：更新发行版时间线并建议版本比较；
- 漏洞撤回或范围收窄：重评估并保留旧结论历史；
- 同一关注规则、漏洞、固件和变化类型只生成一个活动提醒。
